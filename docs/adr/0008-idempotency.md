# ADR-0008. Стратегия идемпотентности

**Статус:** Принято · **Дата:** 2026-09-15

## Решение

Три уровня.

**1. HTTP (`idempotency.Middleware`).** Все изменяющие состояние и денежные `POST`:

- Заголовок `Idempotency-Key` (UUID) обязателен: нет — `400 IDEMPOTENCY_KEY_REQUIRED`, не UUID — `400 IDEMPOTENCY_KEY_INVALID`.
- Хранилище — `platform.idempotency_keys` в PostgreSQL, ключ `(principal, scope, key)`: ключ одного пользователя не раскрывает ответ другому. `scope` = метод + путь.
- `request_hash` = SHA-256(метод, путь, тело).
- Повтор с тем же телом после завершения — исходные статус и тело, заголовок `Idempotent-Replayed: true`.
- Тот же ключ, другое тело — `422 IDEMPOTENCY_KEY_REUSE`.
- Параллельный повтор до завершения — `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`.
- Ответ 5xx освобождает ключ — клиент может повторить.
- TTL 24 ч; просроченный ключ переиспользуется атомарно (`ON CONFLICT … WHERE expires_at <= now()`); очистка — задача `platform.idempotency_cleanup` воркера.

PostgreSQL выбран вместо Redis: запись ключа переживает рестарт кэша, а потеря ключа для денежной операции недопустима.

**Исключение — эндпоинты аутентификации** (`/api/v1/auth/*`): ответы содержат access- и refresh-токены, хранение которых в `idempotency_keys` создало бы копию учётных данных в открытом виде. Повтор этих запросов безопасен по построению: запрос кода создаёт новый вызов, вход создаёт новую сессию, обновление токена защищено обнаружением повторного использования. Ключ на них не требуется.

**2. Доменные операции.** Бизнес-ключи: `(operation_type, reference_id)` в `inventory`, `provider_event_id` для вебхуков PSP, `(saga_id, step)` для шагов саги.

**3. Консьюмеры.** `inbox.Guard` — вставка `(consumer_group, message_id)` в `platform.processed_messages` в одной транзакции с эффектом обработчика.
