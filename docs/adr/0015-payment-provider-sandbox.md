# ADR-0015. Порт платёжного провайдера и встроенный эмулятор PSP

**Статус:** Принято · **Дата:** 2026-09-17

## Контекст

Этап 4 требует сквозной оплаты заказа (FR-PA-01…FR-PA-07), двухстадийной схемы hold/capture, подписанных вебхуков и ежесуточной сверки. Договор с конкретным PSP ещё не заключён, а сквозной сценарий и тесты отказов нужны уже сейчас. NFR-SEC-04 запрещает принимать и хранить реквизиты карт, NFR-SEC-11 требует проверки подписи, защиты от повторов и allowlist адресов, NFR-R-05 — таймаутов и circuit breaker на внешних вызовах.

## Решение

- Контекст `payment` работает с провайдером только через порт `application.Provider`: `CreateIntent`, `Capture`, `Cancel`, `Refund`, `Transactions` (реестр за сутки для сверки) и `Verify` (проверка и разбор вебхука в нейтральный `WebhookEvent`). Реестр `Providers` выбирает адаптер по имени из URL вебхука; новый провайдер — новая реализация и регистрация (раздел 9.2 ТЗ).
- Первый адаптер — эмулятор `internal/payment/infrastructure/psp/sandbox`. Сервер эмулятора монтируется в процессе `api` под `/sandbox/psp` при `PSP_SANDBOX_SERVER=true`, клиент ходит к нему по HTTP так же, как к внешнему PSP. Эмулятор даёт hosted-страницу оплаты с кнопками «Оплатить» и «Отклонить», hold, capture, cancel, частичные и полные возвраты, реестр транзакций. Состояние эмулятора живёт в памяти процесса и теряется при перезапуске — для стендов этого достаточно, потерянные намерения закрываются таймаутом саги и выявляются сверкой.
- Карточные данные не проходят через площадку: покупатель вводит их только на странице провайдера, в систему приходят токен сохранённого способа оплаты и маскированная подпись (`Sandbox Visa •••• 4242`).
- Вебхук подписывается заголовком `X-Sandbox-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>.<body>")>`. Проверка: сравнение в постоянное время, окно ±`PSP_WEBHOOK_TOLERANCE` (5 минут), несколько `v1` для ротации секрета. Эндпоинт `POST /webhooks/payments/{provider}` пропускает только адреса из `PSP_WEBHOOK_ALLOWED_CIDRS` (пустой список — без ограничения, только для dev) и тела до 64 КБ.
- Дедупликация: `payment.webhook_events` с ключом `(provider, event_id)` в транзакции с изменением платежа. Вебхук о неизвестном платеже отвечает 404, чтобы провайдер повторил доставку; конфликтующие переходы (например, отказ после авторизации) подтверждаются без изменений.
- Поздняя авторизация уже отменённого или просроченного платежа отменяется у провайдера (`late-void:<payment_id>`), чтобы не держать hold на карте покупателя.
- Каждая мутирующая операция у провайдера отправляет ключ идемпотентности (`intent:`, `capture:`, `cancel:`, `refund:` + ID), повтор команды не создаёт второго списания или возврата.
- HTTP-клиент: таймаут операции ≤ 5 с, circuit breaker (`internal/shared/platform/breaker`, порог и пауза из конфигурации); бизнес-отказы провайдера (4xx) не открывают breaker. Метрики `external_call_duration_seconds{provider,operation,outcome}`, `circuit_breaker_state{provider}`, `payment_outcome_total{provider,outcome}`.
- Сверка — задача воркера `payment.reconciliation`: сопоставляет платежи дня с реестром провайдера по наличию, сумме capture и сумме возвратов, отчёт хранится в `payment.reconciliation_reports` и доступен поддержке. Расхождения пишутся в лог уровня error для алерта.
- Вне dev-окружения запуск падает, если заданы демонстрационные ключ API или секрет вебхуков либо секрет короче 32 символов.

## Последствия

- Подключение реального PSP не затрагивает домен, прикладной слой и `ordering`: пишется адаптер с тем же портом, его вебхуки приходят на `/webhooks/payments/<name>`.
- Эмулятор не подходит для продакшена: он хранит состояние в памяти одного процесса и не масштабируется горизонтально.
- Реквизиты карт вне области PCI DSS площадки при любом адаптере, пока соблюдается правило «только токены провайдера».
