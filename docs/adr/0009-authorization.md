# ADR-0009. Модель авторизации: RBAC + проверки владения

**Статус:** Принято · **Дата:** 2026-09-15

## Контекст

Роли из раздела 2 ТЗ стабильны и немногочисленны. Требование NFR-SEC-05: покупатель не читает чужой заказ по прямому ID — это атрибут ресурса, а не роль. Полный ABAC с движком политик избыточен для текущих правил.

## Решение

- **Платформенные роли** (`buyer`, `content_moderator`, `support_agent`, `platform_admin`) хранятся в `identity`, передаются в claim `roles` access-токена. Роли → разрешения — таблица в `internal/identity/api` (Published Language), проверка — в прикладном слое каждого обработчика.
- **Роли сотрудников продавца** (`seller_admin`, `seller_operator`) привязаны к конкретному продавцу и хранятся в агрегате `Seller` контекста `seller`. Проверка — через `internal/seller/api`.
- **Владение ресурсом** — доменная политика контекста-владельца (`order.BuyerID() == principal`), проверяется в обработчике после загрузки агрегата или условием read-модели.
- Access-токен: JWT ES256, TTL 15 мин, `kid` для ротации ключей; refresh — непрозрачный, в БД хранится SHA-256 хэш, ротация при каждом обновлении, повторное использование отзывает сессию.
- Блокировка пользователя отзывает все сессии; изменения ролей вступают в силу при следующем обновлении токена (≤ 15 мин).

## Последствия

- Проверки явные и тестируемые unit-тестами обработчиков.
- Переход к ABAC возможен заменой реализации порта `Authorizer` без изменения доменов.
