# ADR-0006. Формат и версионирование доменных событий

**Статус:** Принято · **Дата:** 2026-09-15

## Решение

- Контракт в домене — `kernel.DomainEvent { EventName(); AggregateID(); OccurredAt() }`. Типы событий — структуры без тегов сериализации, имя в прошедшем времени.
- Имя: `<context>.<event_snake_case>.v<N>`, например `ordering.order_paid.v1`.
- Сериализация — в инфраструктуре контекста: `outbox.Codec` сопоставляет тип события с функцией маппинга в DTO; payload — JSON (`JSONB` в `platform.outbox`). Типы payload (`...V1`) и имена событий публикуются в `internal/<context>/api/events.go`.
- Payload самодостаточен: потребитель не обращается синхронно за данными. Суммы — минорные единицы + валюта; идентификаторы — строки UUID; время — RFC 3339 UTC.
- Совместимые изменения (новое необязательное поле) — без смены версии. Ломающие — `v<N+1>`, публикуется параллельно со старой версией до миграции всех потребителей (минимум один релизный цикл).
- Метаданные (`occurred_at`, `request_id`, W3C trace context) — в колонке `metadata` outbox, не в payload; диспетчер восстанавливает из них контекст трассировки.
- Переход на protobuf (`api/proto`, `buf breaking`) — при выделении первого сервиса и подключении внешней шины.

## Последствия

- Домен не зависит от формата; добавление события требует регистрации маппера, иначе запись в outbox завершится ошибкой (проверяется тестами).
