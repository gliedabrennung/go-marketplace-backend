# ADR-0012. Поиск на полнотекстовом движке PostgreSQL

**Статус:** Принято · **Дата:** 2026-09-16

## Контекст

FR-SE-01…FR-SE-05 требуют полнотекстового поиска с морфологией, исправления опечаток, фасетных фильтров, сортировок и полной переиндексации без простоя. Отдельный поисковый кластер (ElasticSearch/OpenSearch) добавляет инфраструктуру, синхронизацию и вторую модель отказа; заказчик ограничил стек PostgreSQL и Redis (ADR-0004 закрепил тот же принцип для доставки событий).

## Решение

- Контекст `search` — read model поверх схемы `search` в той же базе.
- Документ товара: `tsvector`, собираемый генерируемой колонкой `document` с весами `A` (название), `B` (бренд), `C` (описание) по конфигурации `russian`; индекс GIN.
- Атрибуты хранятся как `attributes jsonb` (`код → массив значений`, GIN `jsonb_path_ops`) и `numbers jsonb` для числовых и единичных атрибутов; фильтр по атрибуту — `attributes -> $code ?| $values`.
- Цена, число офферов и состояния товара считаются в `search.product_stats` только по офферам с доступным остатком; таблица пересчитывается при событиях офферов, остатков (`inventory.stock_changed.v1`) и смене статуса продавца, поэтому фильтр `in_stock`, диапазон цены и сортировки по цене не требуют джойнов по офферам.
- Исправление опечаток: `search.lexicon` (`ts_stat` по активной таблице документов) с индексом `pg_trgm`; при нулевой выдаче запрос переписывается по `similarity ≥ 0.4` и повторяется один раз, ответ содержит `corrected_query`.
- Переиндексация без простоя: две версии таблицы (`documents_a`, `documents_b`) и view `search.documents`. Задание пишет в неактивную таблицу, переключает view (`CREATE OR REPLACE VIEW`), затем догоняет изменения, произошедшие во время сборки, по `catalog.Feed` с фильтром `updated_at >= started`.
- Индексация идёт от событий каталога и продавца через outbox (`search.index_products`, `search.index_offers`, `search.index_sellers`).
- Курсорная пагинация: курсор кодирует ключ выбранной сортировки (`rank`, `min_price`, `offers`, `published_at`) и `product_id`.

## Последствия

- Нет отдельного кластера и рассинхронизации между хранилищами; индекс участвует в тех же бэкапах и миграциях.
- Ограничения: нет встроенного «did you mean» уровня поисковых движков, ранжирование ограничено `ts_rank_cd`, фасеты считаются запросом на лету (для больших категорий потребуется кэш или предагрегация).
- При росте до десятков миллионов документов возможен переход на выделенный движок: контракт `search` (`application/query`) и события каталога остаются, меняется только адаптер.
